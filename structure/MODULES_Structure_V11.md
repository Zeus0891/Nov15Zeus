## 🎯 CRITICAL ARCHITECTURAL DECISIONS

### Decision 1: `globalId` in HYBRID Parent Tables

**STATUS**: ✅ MANDATORY

All parent tables in HYBRID modules MUST include `globalId` field:

**Purpose**: Immutable cross-module correlation identifier
**Scope**: Tenant-scoped (has `tenantId`) but globally unique UUID
**Usage**: Links related documents across modules (Estimate → Project → Invoice)
**Format**: UUID v7 (time-ordered for performance)

### Decision 2: `globalId` in PublicLink Tables

**STATUS**: ✅ MANDATORY (Adopted as ERP Standard)

All `<Module>PublicLink` tables MUST include `globalId` field:

**NOT a foreign key** - It's a denormalized mirror of parent's `globalId`
**Purpose**: High-performance correlation without joins
**Benefits**:

- ✅ PublicLinkEngine (GLOBAL) can correlate without tenant access
- ✅ CustomerPortal can filter by `globalId` instantly
- ✅ Unified audit trail across modules
- ✅ Global analytics per document
- ✅ Eliminates expensive joins in public endpoints
- ✅ Simplifies backend code

**Why Mirror Instead of Foreign Key?**

```sql
-- ❌ WITHOUT globalId mirror (expensive):
SELECT e.globalId
FROM EstimatePublicLink epl
JOIN Estimate e ON e.id = epl.estimateId
WHERE epl.token = :token;

-- ✅ WITH globalId mirror (instant):
SELECT globalId
FROM EstimatePublicLink
WHERE token = :token;
```

## 📋 Classification Model

### Module Scope Definitions

**🌐 GLOBAL**: System infrastructure modules (no tenantId on tables)
**🔀 HYBRID**: Modules with tenant tables + public link external access
**🏢 TENANT**: Pure tenant-internal modules (no external access)

### Table Scope (Within Modules)

**GLOBAL tables**: No `tenantId` field
**TENANT tables**: Has `tenantId` field + RLS enforced
**HYBRID Parent tables**: Has `tenantId` + `globalId` (MANDATORY)
**PublicLink tables**: Has `tenantId` + `globalId` mirror (MANDATORY)

## 1. MODULE PLATFORM_IDENTITY

### Tables (11)

**Module**: `identityCore.prisma`
**Scope**: GLOBAL
**Description**: Core identity system for all users and platform actors (system-wide). Maneja autenticación básica y perfil de cuenta **antes** de entrar al contexto de tenant.

### GLOBAL TABLES (11): NO TENANT-SCOPED

- **User** 🏆: System-wide user accounts (email, password hash, base profile). Single source of truth for human identity.
- **Actor**: Abstract identity wrapper (can be `User` or `ServiceAccount`). Used for unified audit logging across modules.
- **Session**: Active authentication sessions and refresh tokens for Users.
- **UserDevice**: Hardware / browser fingerprinting for security alerts and session management.
- **RecoveryCode**: Backup one-time codes for account recovery / MFA bypass.
- **UserHistoryEvent**: Global audit trail of user account changes (signup, email change, password reset, MFA enrollment).
- **UserProfile**: Non-security global profile fields (avatar, bio, display name, locale defaults).
- **UserSetting**: Cross-tenant UI & UX preferences (theme, language, global notification defaults).
- **UserApiKey**: Personal API keys generated by users for programmatic access (scopes, expiration).
- **UserInvitation**: Global invitation tracking (email/phone, source tenant, status) before the user finishes registration.
- **UserDeviceHistoryEvent**: Historical tracking of device usage and device trust events.

> Nota: **ServiceAccount** ya no es global aquí; se mueve al módulo TENANT de Access Control porque sus credenciales y permisos son por tenant.

# HYBRID MODULES

## 6. MODULE ESTIMATE

### Tables (16)

**Module**: `estimate.prisma`
**Scope**: HYBRID
**Description**: Estimate/proposal management for external client review and approval. Clients can view, approve, or decline estimates via public links without login.

### HYBRID TABLES (2): ALL TENANT-SCOPED

- **Estimate** 🏆 ⭐: Core estimate document with **MANDATORY globalId**. Contains pricing, scope, terms for client projects. Enables 1:1:1 traceability with Project and Invoice modules.

- **EstimatePublicLink** ⭐: Token-based public access for external clients.
  **Includes globalId for cross-module correlation. Not a foreign key. Mirrors parent globalId for PublicLinkEngine analytics, portal permissions, and unified audit traceability.** Links to `Estimate`, contains secure token, expiration, allowed actions (view, approve, decline), tracking data (viewCount, lastViewedAt, clientIP).

### TENANT TABLES (14): ALL TENANT-SCOPED

- **EstimateRevision**: Immutable historical snapshots of estimate versions. Audit trail for changes.
- **EstimateSection**: Logical groupings of work items within estimate (e.g., "Foundation", "Framing").
- **EstimateLineItem**: Individual work items with quantity, price, cost, markup. Core pricing data.
- **EstimateTax**: Tax calculations applied to estimate. Supports multiple tax rates and jurisdictions.
- **EstimateDiscount**: Discounts applied to estimate (percentage or fixed amount).
- **EstimateFee**: Additional fees (permit fees, overhead, etc.).
- **EstimateTerm**: Payment and delivery terms (payment schedule, warranty, conditions).
- **EstimateAssumption**: Documented assumptions for estimate accuracy (e.g., "Weather permitting").
- **EstimateExclusion**: Explicit exclusions from scope (e.g., "Electrical not included").
- **EstimateAlternate**: Alternative options for client consideration (upgrade paths).
- **EstimateAttachment**: Header-level documents attached to estimate (drawings, specs).
- **EstimateComment**: Internal collaboration comments on estimate. Not visible to client.
- **EstimateComparison**: Bid comparison records when multiple estimates exist.
- **EstimateHistoryEvent**: Complete audit trail of all estimate changes and state transitions.

### External Access Flow:

```
Internal User → Creates Estimate (with globalId) → Sends to Client
                      ↓
        EstimatePublicLink (mirrors globalId) → Token → Client Access
                      ↓
        Client views/approves → Decision tracked → System triggers:
        Project creation (same globalId), Invoice generation (same globalId)
```

## 23. MODULE TENANT_ACCESSCONTROL (RBAC / ABAC / ReBAC)

### Tables (10)

**Description**: Motor de autorización **por tenant**. Usa el catálogo global de `Permission` + `AccessResource` pero mantiene roles, políticas, scopes y service accounts aislados por tenant. Es la fuente de verdad para RBAC, ABAC y ReBAC interno.

### TENANT TABLES (10): ALL RLS-SCOPED

- **Role** 🏆: Roles definidos por el tenant (ADMIN, PROJECT_MANAGER, ACCOUNTANT, etc.). Metadatos y semántica local a cada organización.

- **MemberRole**: Asignación de roles a `Member` (user-in-tenant). Un `User` puede tener múltiples roles en cada tenant.
- **AccessPolicy**: Políticas ABAC/ReBAC de alto nivel específicas del tenant (ej. “PM puede aprobar estimates > 50k solo si projectType = Commercial”).
- **AccessPolicyCondition**: Condiciones de política (atributos, operadores, valores, time-windows, ubicación, relación con otros actores).

- **ServiceAccount**: Cuentas técnicas por tenant (integraciones, automatizaciones). Se consideran actores no-humanos dentro del tenant.
- **ServiceAccountKey**: Claves/API tokens asociados a `ServiceAccount`. Rotables y revocables por tenant, sujetos a scopes y roles locales.

> Este módulo es el que implementa tu flujo de RBAC + RLS + ReBAC interno, usando `Member` + `MemberRole` y consumiendo el catálogo global de permisos.
